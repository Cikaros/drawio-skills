# 工程化罗盘

改文档、加技能、动脚本之前先读这一页。它解释**为什么这个仓库长这样**，以及哪些决定不能随手推翻。

## 1. 要解决的问题

Agent 第一次用 draw.io MCP 时，必须自己试出：哪个工具会落盘、预览接不接受 `<mxfile>`、边为什么必须带 geometry、容器坐标是相对还是绝对。这些知识每次会话都要重新付一遍探索成本。

本仓库把探索结果固化成三样东西：

1. **Skill**：可安装、可在触发时直接读的操作规范（最短路径）。
2. **校验器**：不依赖浏览器就能判定"这份 XML 会不会坏"。
3. **文档**：解释为什么、边界在哪、哪些还没验证。

目标不是"收集 draw.io 知识"，而是**让下一次会话少走弯路且不撒谎**。

## 2. 两条主线

| | 操作正确 | 结果正确 |
|---|---|---|
| 解决 | 打不开、线不显示、标签变源码、文件被写坏 | 图看不懂、层级混乱、颜色无意义 |
| 形态 | 工具契约、硬规则、lint、失败速查 | 原则、布局、字体颜色、图种验收 |
| 位置 | `docs/drawio-mcp/`、`skills/` | `docs/diagram/` |
| 缺了会怎样 | 交付物直接坏掉 | 交付物"能打开但没用" |

两条线都要，不能只做一半。

## 3. 单一事实源

| 事实 | 唯一位置 | 其它地方 |
|---|---|---|
| 工具契约、实测行为 | `docs/drawio-mcp/pitfalls.md` | 技能里只写结论 + 指针 |
| XML 骨架、样式 | `skills/drawio-mcp/references/xml-cookbook.md` | 文档引用，不复制 |
| 校验规则 | `shared/drawio-lint.mjs` | `references/validation.md` 写规则表 |
| 网格/角色色 | `shared/drawio-guards.mjs` | 文档写数值，测试保证一致 |
| 示例 | `examples/*.drawio` | 文档引用文件名 |

复制粘贴是 drift 的源头。要举例就链接到唯一位置，或让脚本同步。

## 4. 证据等级

| 等级 | 定义 | 写法 |
|---|---|---|
| 实测 | 本轮真实调用/运行过 | 直接陈述 + 日期环境 |
| 源码 | 读上游实现/规范确认 | 注明来源 |
| 推断 | 由已知行为推出 | 标"推断"，并写关闭条件 |
| 未知 | 没验证 | 进 `known-unknowns.md`，不写成事实 |

禁止把"应该"写成"是"。评审时优先质疑没有出处的断言。

## 5. 质量门禁

```bash
npm run check   # 链接、围栏、标题、frontmatter、示例 lint、manifest
npm test        # 纯函数 + 文档契约
npm run verify  # check + test
```

门禁必须**零依赖**（只用 Node 内置模块），否则新环境跑不起来，门禁形同虚设。

新增规则时同时加测试；规则只写文档不写测试，等于没有规则。

## 6. 版本策略

语义化版本 `vMAJOR.MINOR.PATCH`：

- MAJOR：既有用法需要改写（如 XML 骨架变更、工具契约变化）。
- MINOR：新增技能、文档章节、lint 规则。
- PATCH：修正错误、补示例、措辞。

每个版本写 `CHANGELOG.md`；标签只打在通过 `npm run verify` 的提交上。

## 7. 阶段路线

| 阶段 | 内容 | 状态 |

## 8. 决策记录

| 决定 | 理由 | 代价 |
|---|---|---|
| 只写规范，不打包 MCP server | MCP 由部署方提供，仓库管"怎么用" | 用户需自行安装 MCP |
| 自己实现 XML 解析与 lint | 零依赖、可离线、可测试 | 不覆盖全部 XSD |
| 示例图纳入 CI | 防止"文档说的和示例做的不一致" | 示例改动要同步 |
| 技能用中文正文 + 英文触发描述 | 使用者中文，触发靠英文关键词更稳 | 双语维护 |
| 静态站零依赖生成 | 不引入构建链 | Markdown 子集有限 |

## 9. 改东西前的三问

1. 这条结论有证据吗？属于哪一级？
2. 它应该放在唯一事实源，还是只是别处的指针？
3. 加了它，`npm run verify` 还能过吗？需要新测试吗？

答不上来就先别改。
