# 制图原则

图是**论证**，不是装饰。一张图只回答一个问题；回答不了就拆图。

## 1. 一张图一个论点

写图之前先用一句话说清："这张图要让人相信/理解 ______。"

- 好："这张图说明订单在支付超时后如何回滚。"
- 坏："这张图展示系统所有模块。"

后者是目录，不是图。

## 2. 先结构，后样式

顺序固定：

1. 受众与问题（谁看、看完要做什么决定）
2. 节点清单（名词）
3. 边清单（动词/数据流）
4. 分组（边界：系统、团队、部署单元）
5. 布局（方向、层次）
6. 样式（角色色、字号、线型）

跳过 1–4 直接调颜色，通常要返工。

## 3. 语义形状

形状本身要说话：

| 形状 | 含义 |
|---|---|
| 矩形/圆角矩形 | 步骤、组件 |
| 菱形 | 判断、分支 |
| 椭圆/体育场 | 开始、结束 |
| 圆柱 | 数据库、存储 |
| 文档 | 产物、报表 |
| 云 | 外部系统、网络边界 |
| 泳道 | 责任主体 |
| 容器 | 边界（部署、网络、组织） |

同一形状不要在一张图里承担两种含义。

## 4. 层级来自位置，不来自字号

- 主流程一条线，从上到下或从左到右。
- 次级信息放在主节点旁或注释层，不要用 8 号字硬塞。
- 容器表达"属于"，不要用虚线框随手圈。
- 一张图最多三层：系统 → 模块 → 组件；再深就拆页。

## 5. 少即是多

- 节点 ≤ 15 最优，> 25 拆页。
- 边标签 ≤ 3 个词；长解释放节点文字或图注。
- 颜色角色 ≤ 4；线型含义 ≤ 2。
- 去掉不承载信息的装饰（阴影、渐变、图标堆砌）。

## 6. 一致性

- 同一概念同名、同形、同色。
- 同类边同线型、同箭头。
- 同类容器同 `startSize`、同内边距。
- 多页之间保持同一套颜色与命名。

## 7. 可验证

每张图交付前至少能回答：

- 从入口能不能走到出口？有没有孤立节点？
- 每个判断的两条分支是否都有去向？
- 每个异常是否有处理或明确"不处理"？
- 图里的数字、名称与源文档是否一致？

## 8. 与 AI 协作的边界

- **AI 负责**：结构草案、XML 生成、静态校验、批量重排、文案压缩。
- **人负责**：论点、取舍、术语、最终目视验收。
- **共同**：把"不确定"标出来（`known-unknowns.md`），不要用漂亮图掩盖没想清的地方。

## 9. 反模式

| 反模式 | 后果 | 替代 |
|---|---|---|
| 把所有模块画进一张图 | 读者找不到主路径 | 总览页 + 细节页 |
| 每个节点一种颜色 | 颜色失去含义 | 按角色配色 |
| 用 3D/阴影强调 | 视觉噪音 | 加粗边框或换位置 |
| 边标签写整句 | 线被文字淹没 | 3 词以内，解释放图注 |
| 用图代替文字规范 | 无法检索、无法 diff | 图 + 一页文字说明 |
